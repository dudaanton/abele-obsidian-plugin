# External file representation and projection work

Task six connects an opt-in classifier and durable projection jobs to ordinary personal and scoped sync. No UI, automatic eviction or production eviction/hydration API has been enabled. The pinned core and protocol come from the exact revision in `External file implementation inputs.md`; startup now gives the personal engine core's shared `RecoveryBarrier` after the host validates ownership, binding and journals. The host's point-of-effect fences remain authoritative after a long await. Existing constructors are still deferred until recovery, rather than using the new barrier as a reason to construct early.

## Common local representation

`external/representation.ts` wraps core's filesystem, ledger and personal/scoped clients under a single local-representation classifier. Intentional missing originals are neither deleted nor dirty. Known or recognizable sidecars, including moved/damaged files, and unexpected originals are held out of scanner, SHA indexing, dirty/scope review, scoped folder-native create, pull/prefetch and push/replay. Ordinary non-projection `.abele-ref` files keep ordinary behavior. Watchers still report actual events; no path-wide watcher suppression is introduced. Replay checks managed file identities and both endpoints before committing; equality of hashes never establishes scoped ownership. Accepted server metadata lives in the existing personal/scoped head authority, not a second scoped head table. An unexpected original retains its previous proven local base, including across a remote metadata version advance or its later disappearance.

The classifier stat-checks and prefix-reads candidate files, bounded to 16 KiB on hosts with a prefix/native descriptor and to the 200 MiB attachment limit on the portable adapter. Known paths and migration evidence do not depend on finding a marker in the file. Inspection never converts projection JSON into an upload. Changed/occupied sidecars stay on disk. Classified collisions cannot silently become a new path. Scope/filter eligibility (including the current configurable scripts folder) is checked again before projection installation; code/settings moves require the existing approval/deferred path and are not installed as attachments. Exclusion does not enroll a file in sync again.

## Durable event acceptance

The personal wrapper commits the accepted head and projection intent together in the existing IndexedDB transaction, before returning the event page to core to advance its cursor. Filtering an external-only feed page must not look like end-of-feed: the wrapper follows to the next page until it reaches real events or the actual head. Scoped snapshots first collect the complete anchored inventory with its terminal feed proof; then current authorized heads create projection jobs. Scoped feed/checkpoint work refuses checkpoint advancement if durable intent or scoped-head recording fails. On retry, an already committed job repairs a previously failed scoped-head write rather than creating another job. The actual checkpoint remains in `ScopedState`; no independent scoped head table is introduced.

Projection jobs retain operation ID, expected file/version/path/SHA/size, generation, prior base, target, digest and an owned staging reference. The client obtains exact live-head verification for a new content version before writing a projection; a verification failure holds the prior projection/job. There is no client blob GET for remote-only metadata. A job is recorded before staging or any disk write. Ordinary initial projection creation uses the selected task-five installer. A pre-existing or changed sidecar is preserved and marked `cleanup-pending`, never overwritten even when it matches. A lost installation acknowledgement is held, not retried based on matching bytes. A restart with an outstanding projection intent cannot infer whether it wrote a target: it records a recovery hold rather than blindly installing. Safe verified no-effect holds can be reconsidered without an event replay.

A rename preserves file identity/preference and the old sidecar until safe retirement is possible. Delete creates a tombstone; scoped departure records detach separately; restore keeps preference and requires fresh eligibility/verification. Unsupported logical remote-only rename/delete is not exposed as a local sidecar edit. Unavailable proofs and access loss keep retained evidence. No consumer calls `evict()` automatically.

## Verification and limits

- Fast fake-IndexedDB and fake-vault tests cover classification, ordinary sidecars, scanner/SHA/dirty/replay refusal, one commit before cursor, scoped snapshot/feed, interrupted phases, tombstones/rename/restore, earlier base, access revocation, code/settings eligibility and policy changes.
- A real selected-revision Fastify server test covers a personal two-device metadata update with no client blob GET, create/upload/delete, and a persisted projection hold.
- Live desktop and iPhone adapter tests use distinct synthetic directories and actual IndexedDB; they cover staging and projection creation for a missing sidecar, scoped folder-native scan, transition state, restart reopening after cursor advancement and approval after scripts-folder changes. They do not claim a full attachment API/server round trip on either device.

Unsupported old direct-delete behavior, power-loss durability, independent filesystem writers and the accepted final deletion/rename races remain as described in `External file durable state.md` and `External file filesystem ports.md`. The unsafe iOS adapter-copy assertion remains unchanged; no projection or hydration path uses copy.
